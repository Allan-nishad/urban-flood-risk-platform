## 1. Audit Context & Scientific Objective

In Phase 4.2, the platform implemented programmatic ingestion of forward-looking precipitation forecasts from the Open-Meteo API using an ensemble blend of ECMWF IFS ($9\text{ km}$) and NOAA GFS ($13\text{ km}$). The Phase 4.2 report claimed that separating `forecast_issue_time` from `valid_time` and enforcing non-negative `lead_time_hours` guaranteed zero forward-looking data leakage.

The scientific objective of this audit is to determine:
1. Exactly where the values in `forecast_issue_time`, `retrieval_time`, `valid_time`, and `lead_time_hours` originate.
2. Whether the numerical weather prediction (NWP) model's true initialisation cycle time ($00\text{Z}, 06\text{Z}, 12\text{Z}, 18\text{Z}$) was provided by the upstream API or generated by the local client application.
3. Whether non-negative lead hours mathematically prevent data leakage during historical retrospective evaluations.

## 2. Source Code & Data Inspection

Inspection of [`src/floodrisk/ingestion/forecast.py`](file:///c:/Users/allan/Documents/Projects/urban-flood-risk-platform/src/floodrisk/ingestion/forecast.py) (lines 57–58, 110–125) reveals:

```python
retrieval_time = datetime.now(timezone.utc).isoformat()
issue_time = datetime.now(timezone.utc).strftime("%Y-%m-%dT%H:00:00Z")
```

And in the per-step loop:

```python
issue_dt = datetime.fromisoformat(issue_time.replace("Z", "+00:00"))
valid_dt = datetime.fromisoformat(t_str + ":00+00:00")
lead_hours = int((valid_dt - issue_dt).total_seconds() // 3600)
```

### Critical Findings:
1. **Model Cycle Initialisation Time is Unexposed:**  
   The Open-Meteo free standard endpoint (`https://api.open-meteo.com/v1/forecast`) provides hourly precipitation arrays indexed by timestamps (e.g., `2026-11-05T10:00`), but does **not** expose the underlying numerical model's base cycle initialisation time (e.g., `2026-11-05T00:00:00Z` or `2026-11-04T18:00:00Z`).
2. **`forecast_issue_time` was Locally Inferred:**  
   The field labelled `forecast_issue_time` was constructed by rounding the local client's download timestamp (`retrieval_time`) to the top of the current UTC hour. It represents a **retrieval reference timestamp**, not the actual meteorological model run initialisation time.
3. **Calculated Lead Time is Client-Relative:**  
   Because `lead_time_hours` was computed as `valid_dt - issue_dt` (where `issue_dt` is the retrieval hour), the lead time measures hours from data acquisition, not hours from model initialisation. For example, if ECMWF ran at $00\text{Z}$ and the data was retrieved at $10\text{Z}$, a valid time of $12\text{Z}$ has a true model lead time of $12\text{ hours}$, but client-relative lead time was recorded as $2\text{ hours}$.
4. **Data Leakage in Retrospective Backtesting:**  
   Non-negativity of client-relative lead time (`lead_hours >= 0`) guarantees physical causality only in real-time forward operations. In retrospective historical evaluations, if archived forecasts are downloaded after the event date without strict logging of historical model run availability, forward-looking model updates could leak into past event reconstructions.

## 3. Targeted Schema & Pipeline Corrections

To eliminate scientific ambiguity, the following structural corrections have been implemented in [`src/floodrisk/ingestion/forecast.py`](file:///c:/Users/allan/Documents/Projects/urban-flood-risk-platform/src/floodrisk/ingestion/forecast.py):

| Field Name | Previous Implementation | Corrected Implementation & Definition |
| :--- | :--- | :--- |
| `forecast_issue_time` | Inferred retrieval hour string | Retained for backward schema compatibility, but renamed semantically in documentation. |
| `nominal_reference_time_utc` | *Not present* | **Added.** The nominal hourly reference time anchor used by the client application. |
| `retrieval_time_utc` | *Unstandardized* | **Standardized.** ISO 8601 UTC timestamp recording exact HTTP download execution. |
| `model_initialization_status` | *Not present* | **Added.** Explicit flag: `"UNEXPOSED_BY_PROVIDER_INFERRED_FROM_RETRIEVAL"`. |
| `source_resolution` | Coarse note | **Formalized.** `"approx. 9-13 km (ECMWF IFS/GFS coarse anchor)"`. |
| `coarse_grid_note` | *Not present* | **Added.** `"Inherited from nearest 9-13km regional anchor; not an independent 1-km weather observation."` |

## 4. Retrospective Leakage Safeguards for Phase 5

For future historical validation (Phase 5):
1. **Rule of Historical Availability:** A forecast run initialized at time $T_{\text{init}}$ may only be used to evaluate decisions at time $T_{\text{decision}} \ge T_{\text{init}} + \Delta T_{\text{latency}}$, where $\Delta T_{\text{latency}} \approx 4\text{ to }6\text{ hours}$ represents operational dissemination delay (ECMWF IFS runs take ~4.5 hours to compute and distribute).
2. **Archival NWP Provenance:** Historical forecast skill evaluations must acquire explicit model cycle archives (e.g., ECMWF MARS or NOAA NOMADS GFS historical cycle files) where $T_{\text{init}}$ is cryptographically stamped in GRIB2/NetCDF metadata.
